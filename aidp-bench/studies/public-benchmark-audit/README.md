# Ground-truth audit of ten public document-AI benchmarks

Built 2026-10-22 02:12 IST. Every verdict below points at a saved file, and every number was re-read from the saved evidence when this page was generated.

For publication on 22 October 2026, every quotation of a public dataset's own files (its answers, questions, page text and README sentences) was replaced by a pointer to the file, line or record it came from, except a few short values from CORD, whose CC BY 4.0 licence allows them with credit (CORD: Park et al., 2019, https://github.com/clovaai/cord). Where a dataset's own file or
column names name commercial extraction systems or models, counts replace the names. No count and no verdict changed.

## What this is, in plain words

A benchmark is a public collection of documents (receipts, forms, invoices, reports) plus an answer key. The answer key, also called ground truth, is the file that says what the right answers are, so a system's output can be marked right or wrong. Section 5 of the white paper 'Precision Beyond the Page' compares the answer keys of ten public benchmarks on fifteen kinds of information, as a matrix (a grid of benchmarks against properties). This folder is that audit, with every piece of evidence kept.

For each benchmark the actual answer files were downloaded (annotation files only, no image sets), scanned by small scripts that count what is there, and judged property by property. Each judgement, called a verdict, is one of three words:

- present: the answer key holds this kind of information, in the sense of the written rule for that property.
- partial: the key holds some of it: only implicitly, only by accident, only for some fields, or only for some documents.
- absent: the key does not hold it.

A few terms used throughout:

- Field: a named slot for one piece of information, such as 'total' or 'invoice date'.
- Printed form and canonical form: the printed form is how a value looks on the page (60.000, 31 March 2016). The canonical form is the one standard way of writing it that a computer system expects (60000.00, 2016-03-31). Converting one into the other is called normalisation.
- Bounding box: the rectangle on the page where a value sits, given as coordinates. It is the evidence location of the value.
- Invention: a system returning a value for a field that the page leaves empty. You can only catch it if the answer key records that the field is empty.
- Decoy key: a field a system is asked for that has no answer in the document, on purpose.

## The short answer

- Normalisation: CORD's test row 0 stores the price as the text 60.000 and never as 60000.00, while both Kleister datasets store normalised dates, money and terms where the pages print other forms.
- Invention: SROIE's test answers have no empty field at all, so they cannot show a system inventing a value. Kleister (declared decoy keys) and VRDU (its scorer counts answers for missing fields) can.
- Never-printed values: both Kleister datasets hold some, by accident and unmarked; no dataset marks them.
- Evidence locations: DocILE and VRDU attach a box to every answer.
- Payload keys, derivability flags and rule ground truth are absent from all ten.
- Every corpus distributes its documents, so repeatability can be measured on all ten.

## Method

1. The fifteen properties are the answer-key information AIDP's measures need (white paper, section 5). AIDP-2K's own keys carry most of them, but not yet evidence locations, customer reference records or full derivability flags. They are: per-field keys, explicit empties, canonical beside printed, values never printed, evidence locations, derivability flags, planted traps with controls, declared difficulty, instruction (rule) ground truth, payload keys, line-item and table row structure, document type labels, multi-document segmentation boundaries, entity resolution targets and repeatability.
2. For each benchmark the smallest set of files that contains the answer key was downloaded: sparse git checkouts of only the annotation folders, the Hugging Face rows API with the image column dropped, and HTTP range requests that read single files out of large zip archives without downloading the rest. Each download went into its own new folder under samples/. Downloaded files were treated as untrusted data: scripts live in scripts/ and were run with python3 -I, with paths passed as arguments.
3. One script per benchmark (scripts/scan_*.py) reads every downloaded annotation record and writes counts to evidence/*.json: which keys exist, how many values are empty, how values are written, which carry positions, and so on. An absence verdict is based on the full list of keys that occur in the files, not on not noticing something.
4. scripts/build_matrix.py holds the 150 verdicts with their evidence and sources, re-reads every quoted number from evidence/*.json and stops if any number no longer matches, then writes matrix.json and this README.
5. Where the text of a paper or README was needed (for example how Kleister made its answers), the text was saved under samples/ and is cited by line number.
6. Times are India Standard Time (IST, GMT+05:30).

## The fifteen properties and the rule for each verdict

1. per-field keys. Paper's wording: per-field keys. Measure it serves (this audit's mapping): Completeness and Fidelity (Capture). Rule: present: each answer is stored under a named field from a fixed schema. partial: answers are keyed, but to free text (a printed label or a question) rather than a fixed set of named fields. absent: no field-level answers (page transcription, layout or table structure only).
2. explicit empties. Paper's wording: explicit empties. Measure it serves (this audit's mapping): Restraint (values invented). Rule: present: for each document the key states which fields were asked and which have no value (explicitly, or by a documented rule that an asked field left out of the key means 'no value'), so a value returned for an empty field is a countable false positive. partial: emptiness is only implied by omission from a closed field set (sometimes enforced by the scorer), or recorded only as empty table cells. absent: empty fields cannot be told apart from unannotated ones, or the scored split has no empty field at all.
3. canonical beside printed. Paper's wording: canonical beside printed. Measure it serves (this audit's mapping): Normalisation (Understand). Rule: present: the key stores both the printed form and a normalised (canonical) value. partial: the key stores the canonical value only (the printed form stays in the page or its OCR text, not beside it), or only for some fields. absent: the key stores the printed form only.
4. values never printed. Paper's wording: values never printed. Measure it serves (this audit's mapping): Computation and Attribution (Understand). Rule: present: the key deliberately includes answers the page does not print (inferred, computed or looked up) and marks them. partial: such answers exist but incidentally and unmarked. absent: every answer is printed on the page, either as written or merely reformatted. Document-level classification labels (type, language) are judged under property 12, not here.
5. evidence locations. Paper's wording: evidence locations. Measure it serves (this audit's mapping): Traceability (Trust). Rule: present: every answer (or every annotated element, for parsing corpora) carries its position (box or polygon plus page, or character offsets). partial: positions exist for text lines but are not linked to the answers. absent: no positions.
6. derivability flags. Paper's wording: derivability flags. Measure it serves (this audit's mapping): Computation (Understand). Rule: present: the key marks whether a missing value can be derived from other values. partial: some derived values are marked. absent: nothing in the schema records derivability.
7. planted traps with controls. Paper's wording: planted traps with controls. Measure it serves (this audit's mapping): Escalation (Trust) and Consistency (Understand). Rule: present: the corpus plants known defects and pairs them with matched clean controls, and the key says which is which. partial: planted defects without controls, or controls without a key. absent: natural documents only.
8. declared difficulty. Paper's wording: declared difficulty. Measure it serves (this audit's mapping): reporting by difficulty (section 6 difficulty study). Rule: present: every document (or page) carries declared difficulty labels or a declared hard subset. partial: per-document attributes that are known difficulty factors, or per-document membership in a harder evaluation condition (unseen layout or template), without a grade. absent: nothing per document.
9. instruction ground truth. Paper's wording: instruction ground truth (also called rule ground truth). Measure it serves (this audit's mapping): Instructions (Reason). Rule: present: correct outputs under written customer rules, with an untouched baseline. absent: no rules.
10. payload keys. Paper's wording: payload keys. Measure it serves (this audit's mapping): Decoding (Understand) and barcode payloads (Read). Rule: present: decoded barcode or QR contents are stored. absent: no encoded-content field.
11. line-item / table row structure. Paper's wording: line-item / table row structure. Measure it serves (this audit's mapping): Line items (Capture). Rule: present: the key groups values into rows or line items. partial: tables exist only as unstructured text. absent: no row structure.
12. document type labels. Paper's wording: document type labels. Measure it serves (this audit's mapping): Identification (Capture). Rule: present: each document carries a type label from a set of more than one type. partial: type implied only by sub-corpus or file name. absent: single-type corpus with no label, or no label.
13. multi-document segmentation boundaries. Paper's wording: multi-document segmentation boundaries. Measure it serves (this audit's mapping): Segmentation (Capture). Rule: present: files holding several documents carry the boundaries. absent: one document per file, or multi-document files removed.
14. entity resolution targets. Paper's wording: entity resolution targets. Measure it serves (this audit's mapping): Resolution (Reason). Rule: present: printed names are linked to entries in a master list or registry that contains plausible wrong candidates. partial: the key carries a registry identifier for the real entity, sourced from the registry, but no candidate list. absent: names stored only as printed.
15. repeatability needs (documents only). Paper's wording: repeatability (needs only documents). Measure it serves (this audit's mapping): Repeatability (Trust). Rule: present: the documents themselves are distributed, so the same document can be submitted twice and the outputs compared; no answer key is needed. absent: documents not available.

## Limits of this audit

- The verdicts are judgements made against written rules. The borderline ones are marked partial and explain themselves (for example DocVQA's question-type tags counted as partial declared difficulty, and table corpora's empty cells counted as partial explicit empties). Someone applying a stricter rule could move those cells to absent; none of the corrections above depends on a borderline cell.
- CORD: only the test and validation splits (200 receipts) were scanned. The rows API returned HTTP 500 for every request on the 800-receipt train split. The paper's claim concerns the test split, which was read in full.
- DocILE is access-gated. It was judged from its published schema, its evaluation code, its paper and the one real annotation file its repository publishes, not from the full annotation set.
- Kleister's test answers and DocVQA's test answers are withheld by their authors; the train and dev (Kleister) and validation (DocVQA) answers were used.
- DocVQA: 4 of its 33 yes/no answers were checked against their page images (all print the answer word); the other 29 were not.
- The checks that a Kleister answer is 'not printed' search four independent OCR text layers. One case was confirmed against the PDF itself (39 pages, text layer on every page, not even the stored number's first three digits anywhere, the two image-heavy pages viewed).

## Files in this folder, and how to rebuild

- matrix.json: the 150 verdicts (benchmark, property, verdict, evidence, source with local path, record and URL, date checked in IST), the property rules, per-benchmark download notes, and counts.
- evidence/: one JSON file of counts per scan, plus summaries of the RD-TableBench and FUNSD archive listings. For publication, the example records the scans save beside their counts (values, questions, answers and page text quoted from the datasets' own files) were removed, apart from CORD's; every count is unchanged, and the scans write the examples again when rerun.
- scripts/: the fetch, scan and build scripts. Rebuild with: python3 -I scripts/build_matrix.py <this folder>, after fetching samples/: the build re-reads the downloaded files to check each verdict's evidence. The scans can be rerun from the files in samples/ with the commands given at the top of each script. samples/ is not published, because the downloaded files belong to their authors; fetch them again from the sources listed below.
